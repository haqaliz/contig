## Design pins

- **Capture condition (QC-driven only):** `RunSummary.from_events(record.events)
  .succeeded` AND `record.qc_results` non-empty AND
  `overall_verdict(record.qc_results) in {"fail", "warn"}` AND
  `record.verification_inputs` non-empty. (The events guard prevents labeling a
  crash's `verdict == "fail"` as a verification verdict — same guard as
  qc_anomaly, self_heal.py:1041-1045; WARN added because concordance/plausibility
  can only WARN.)
- **Choke point:** `runner._finalize` — every completed run (clean, self-healed,
  qc-flagged) passes through it with `record` and `runs_dir` in scope. Add the
  capture there. Verify `_finalize`'s signature and call sites before wiring;
  if `_finalize` lacks `runs_dir`/`pending` plumbing, thread a
  `pending_verify_corpus: Path | None = None` parameter defaulting to
  `<runs_dir>/pending_verify_corpus.jsonl` (additive, back-compat).
- **`verification_inputs` capture inside `_discover_qc`:** collect the metric
  dicts already computed at these exact sites:
  - `multiqc` family: the `metrics` dict from
    `parse_multiqc_general_stats_file` inside `evaluate_run_qc`
    (run_qc.py:35-38) — or re-derive in `_discover_qc` by calling
    `parse_multiqc_general_stats_file(multiqc)` once and passing it down;
    prefer the least invasive: compute in `_discover_qc` where `multiqc` is
    already located, and have `evaluate_run_qc` accept the pre-parsed dict
    (additive optional arg, back-compat) OR keep `evaluate_run_qc` untouched
    and parse twice (a JSON read; simple and safe). Integrator picks; both
    keep the dict available.
  - dedicated-gate families: the `located` dicts already built per assay in
    `_discover_qc` (rnaseq composition, scrnaseq, methylseq, ampliseq, mag —
    runner.py:194-281 pattern) right before their `evaluate(located, pack)`.
  - `germline` family: `evaluate_variant_plausibility` computes ts_tv/het_hom/
    variant_count from the VCF — the metric dict is inside variant_metrics.py;
    capture needs a seam. Least invasive: add an optional
    `capture_metrics: dict | None` out-param or return the dict alongside
    results (additive return change — check call sites; only runner calls it).
    If this proves invasive, `germline` is excluded from slice-1 CAPTURE (still
    in the seed) and documented in the code comment — the plan allows that
    explicit narrowing; the capture condition then keys on whatever families
    ARE captured (non-empty check stays).
- **Family names must match the aspect-1 scorer table exactly**
  (`multiqc`, `rnaseq_plausibility`, `rnaseq_composition`, `somatic_plausibility`,
  `annotation_plausibility`, `scrnaseq`, `methylseq`, `ampliseq`, `mag`,
  `germline`, `concordance`).

     `verification_inputs=capture_inputs` in the record build (runner.py:1230).

- **Validation:** `uv run pytest tests/test_verify_capture.py`; full suite green

## Phase 2: pending capture at finalize (TDD)

- **Goal:** QC-driven WARN/FAIL runs append one pending VerificationCase.
- **Files:** `src/contig/runner.py` (or `verify_corpus.py` builder +
  `runner.py` wiring), `tests/test_verify_capture.py`.
- **Steps:**
  1. RED: tests —
     - a green-events run record with `qc_results` reducing to `fail` and a
       populated `verification_inputs` → finalize appends exactly one case with
       `source="pending:<run_id>"`, `expected_verdict=None`, `known_miss=False`,
       and the inputs copied.
     - same with verdict `warn` → appended.
     - verdict `pass` → nothing appended.
     - a record with failed events (crash) → nothing appended.
     - `verification_inputs=None` with a FAIL verdict → nothing appended
       (honest: nothing band-relevant to label).
     Use injected fixtures (write a record to a tmp dir, call the finalize
     seam with a tmp `pending_verify_corpus` path; mirror how
     test_qc_anomaly_capture.py drives `_finalize`).
  2. GREEN: `verification_case_from_run(record, *, pending=True)` builder in
     verify_corpus.py (mirror corpus.py:107-129): `case_id=f"{run_id}-verify"`,
     `description` stating assay + driving verdict + captured families;
     wire the append in `_finalize` (additive `pending_verify_corpus` param).
  3. REFACTOR: extract the capture predicate as a pure function
     (`should_capture_verification(record) -> bool`) for testability.
- **Validation:** `uv run pytest tests/test_verify_capture.py`; full suite green.
- **Commit:** `feat(verify): capture pending verification cases from WARN/FAIL runs (C6 fold-in)`

## Phase 3: verify-case-promote (TDD)

- **Goal:** `contig verify-case-promote` CLI + `promote_pending_verify_case`.
- **Files:** `src/contig/verify_corpus.py`, `src/contig/cli.py`,
  `tests/test_verify_promote.py`.
- **Steps:**
  1. RED: `tests/test_verify_promote.py` —
     - promote with `--expected-verdict warn` → case appears in golden with
       `source="confirmed:<run_id>"`, `expected_verdict="warn"`, removed from
       pending; echo names it.
     - promote without `--expected-verdict` → keeps `None` (still moves; the
       reviewer may only confirm). (Confirm this choice: PRD R5 says
       "confirm or correct" — promote must allow label-less confirmation.)
     - unknown case id → exit 1, pending untouched.
     - duplicate id in golden → exit 1 naming the dedupe.
     - auto-snapshot: golden-history `verify_history.jsonl` gains one
       `VerifySnapshot` line whose `case_count` matches the grown golden.
     - invalid `--expected-verdict` value → exit 1 (before any write).
  2. GREEN: `promote_pending_verify_case(case_id, *, pending_path, golden_path,
     expected_verdict=None)` in verify_corpus.py (mirror corpus.py:140-181:
     find → dedupe → `model_copy(update={"expected_verdict": ...,
     "source": confirmed_source})` → append → rewrite pending) and the CLI
     command mirroring `corpus-promote` (cli.py:2376-2417) including the
     auto-snapshot: `report = evaluate_verify(load_verify_cases(golden))` →
     `snapshot_from_verify_report` → `append_jsonl` to the default history.
- **Validation:** `uv run pytest tests/test_verify_promote.py`; full suite green.
- **Commit:** `feat(cli): contig verify-case-promote — human label channel for verification cases (C6 fold-in)`

## Environment & reproducibility

- Pending corpus lives under `runs/` (like `pending_corpus.jsonl`); golden is
  committed data (`src/contig/data/verify_corpus.jsonl`). Pending files are
  never signed (corpus data, not bundles) — no signature impact.

## Edge cases & error handling

- `verification_inputs` present but empty dict → treated as None (skip).
- A WARN verdict driven only by un-captured families (e.g. structural) →
  inputs empty → skip (honest).
- Promote of a case already promoted → error naming it (dedupe by case_id).
- Malformed pending line → skipped on load (blank-line precedent).
- `--expected-verdict` validation reuses the `QCStatus` literal values; reject
  anything else before touching files.

## Agent execution notes

- The `_discover_qc` seam (Phase 1) is the riskiest change — keep
  `_discover_qc(run_dir, assay)` signature stable and route the capture through
  the out-param; run the full suite after Phase 1 before touching `_finalize`.
- `_finalize` may be called from more than one site — verify callers
  (`grep -rn "_finalize(" src/`) and keep the new param defaulted so every
  caller is unchanged.
- Checkpoint: after Phase 2, run a synthetic end-to-end (build a run dir with
  a failing fixture, run `contig verify-case-promote` on the captured id) as
  the manual gate before the final commit.
